# hooks

Three hooks, all registered in `.codex/hooks.json`: `guard.mjs` and `backend-guard.mjs` as `PreToolUse`, and `upkeep-nudge.mjs` (end of this file). `guard.mjs` is registered twice: as `PreToolUse` for `Bash`, `apply_patch` and the two tools that start or task another agent, where it judges the call, and as `SessionStart`, where it only forgets which path rules a lost context was shown. `backend-guard.mjs` is registered for `Bash` and `apply_patch`. A `PreToolUse` hook reads one JSON payload on stdin. **To refuse, it prints one JSON object on stdout and exits 0** - `{"hookSpecificOutput":{"hookEventName":"PreToolUse","permissionDecision":"deny","permissionDecisionReason":"..."}}` - and the reason reaches the model verbatim; to allow, it prints nothing. Codex runs both guards on a call side by side, and either one's refusal stops it. **A guard that cannot parse its input allows the call**: each is a backstop, never a security boundary. Node 18+, no dependencies - the hooks are Node scripts whatever language the service is written in.

**The `--harness codex` flag on their command lines is what makes them speak this protocol.** `guard.mjs` and `backend-guard.mjs` are files shared with a Claude Code layer; without the flag they answer in that tool's form (an exit code and stderr, and for `backend-guard.mjs` a question to the user), which blocks nothing here. Their header comments and their messages' source text describe that other form - the flag rewrites the messages for this one. Never drop the flag from `hooks.json`.

**The command line** is `node "$(git rev-parse --show-cdup).codex/hooks/<hook>.mjs" --harness codex`: no variable carries the project root and a hook starts in the session's directory, which may be a subfolder, so git names the way up from there (`../../`, or nothing at the root). It is a relative path on purpose: PowerShell decodes a native command's output with the console code page, so an absolute root with non-ASCII letters (`--show-toplevel`) came back garbled and the hook did not start. That line works in PowerShell 7, Windows PowerShell, `bash` and `sh`. Each guard then takes the project root from its own location, never from the working directory. Outside a git repository the line fails with empty output, which allows the call.

**Trust.** Codex loads a project's `.codex/` only for a trusted project, and runs only the hooks the developer has reviewed: `/hooks` in the CLI, Settings > Hooks in the app. **A new or changed hook is skipped until it is reviewed again, and Codex says nothing about it** - after an install or an update of this layer, or any edit to `hooks.json` or a hook script (a project list entry included), open the review; until then nothing here guards anything, and only `.codex/rules/git.rules` still refuses the plain git verbs it lists. Review both guards together: one trusted without the other leaves secrets and migrations, or git and the tree, unguarded. The check, one call each: have Codex run `cd .` - a refusal beginning "Blocked by .codex/hooks/guard.mjs" means `guard.mjs` is live - and `Get-Content .env.layer-probe` - a refusal beginning "Blocked by .codex/hooks/backend-guard.mjs" means `backend-guard.mjs` is; a command that simply runs (a missing file is that) means that hook is off. `AGENTS.md` has every session make both checks itself before its first edit.

`guard.mjs` is the same code in both layers of this bootstrap and knows nothing about servers; `backend-guard.mjs` holds what a server codebase adds. Keep them apart: a new check about files and git goes into the first, one about data, secrets or the outside world into the second.

## guard.mjs - what it refuses

**A shell call** (`Bash`, whatever the shell - judged by PowerShell grammar on Windows and by Bash grammar elsewhere)

- A git verb that commits, stages, publishes or discards work - wherever a shell runs git, judged on the words it receives (a quoted `-C "D:/Work Projects/x"` is one word): at command position behind `git -C` or `git -c`, a wrapper, `npx` or a launcher (`xargs`, `find -exec`, `Start-Process`), inside `$(...)`, `cmd /c`, a `bash -c` / `iex` body, as a quoted full path to the binary; and anywhere inside code an interpreter runs (a `node -e` / `python -c` / `perl -e` one-liner, a script fed on stdin or piped into `bash`). Git words in an argument are text (`echo "never git push"`), and so is the pattern of a search behind `xargs` or `find -exec` (`git ls-files | xargs grep -n "git commit"`). `git stash` is judged by an allow list (`list`, `show` pass); `git send-email`, `subtree` writes, `lfs push` / `migrate` (not `lfs pull`) and a `fetch` into a local branch count too. A tool that commits or tags through git: `npm` / `pnpm` / `yarn version` (unless `--no-git-tag-version`), `release-it`, `standard-version`, `semantic-release`, `lerna version` / `publish`, `changeset publish`. A read git verb that runs a program or writes a file - `git grep -O<cmd>` / `--open-files-in-pager`, any verb's `--output=<file>`. A `gh` call that writes - judged, like the in-place tools below, where a shell runs it: in another command's quoted argument the words are text (`echo "next: gh pr create"`, `npm test -- -t "sed -i"`), unless that command runs the text (an interpreter's code, a launcher, a script fed on stdin).
- A write into the tree from the shell: an in-place edit (`sed -i`, `perl -i`, `ruby -i`, `yq -i`, `prettier --write`, `eslint --fix` and `stylelint --fix` however they are started, and other stacks' formatters - `black`, `isort`, `ruff format`, `gofmt -w`, `goimports -w`, `go fmt`, `golangci-lint run --fix`, `dotnet format`, `dotnet csharpier`, `cargo fmt` and the like, unless a check flag keeps them read-only; a project's own task such as `./gradlew spotlessApply`, `make fmt` or a `format` package script passes. A formatter this project runs that is not on the list: the developer adds its form to `formatterWrites` in `guard.mjs`, with a case in `tests/guard-shell-test.mjs`.), sed's `w` command, `sort -o`, a redirect (a quoted target is read whole, blanks included), `Set-Content` / `Add-Content` / `Out-File` (or, in PowerShell, `sc` / `ac`) whose target is a project path, a copy or move whose destination is inside the project, an interpreter one-liner, or a script an interpreter reads on stdin (`python - <<'EOF'`), that opens a file for writing (pathlib's `write_text` included). sed's `e` command runs a shell and is always refused. A Bash variable a leading statement sets to a literal (`O="/tmp/out"; cp a "$O/b"`) is judged as that literal, and one set from `mktemp` (`T=$(mktemp); npm ls > $T`) or PowerShell's `New-TemporaryFile` as scratch; one the rest of the command may rebind stays unresolved and is refused. A heredoc body no shell reads (`cat > /tmp/x <<'EOF'`, `python3 - <<'EOF'`, `psql <<'SQL'`) is not judged as commands; one a shell reads is.
- A delete beyond the one grant: one non-recursive project path per call (cmd's `/s` counts as recursive, clustered as `/s/q` too), never a glob (a quoted `[...]` name that exists as written, such as `"app/blog/[slug]/page.tsx"`, is that one file), never a `PROTECTED_PATHS` match, `.git` or one of the layer's own files (below).
- A mover, deleter or downloader named with its `.exe` / `.com` suffix or by its full path (`rm.exe`, `/usr/bin/rm`, `curl.exe`, `cmd.exe` by its path) is judged by its bare name; a relative path such as `./install` is a project script and keeps its name.
- A `cd` or `Set-Location` anywhere in the command, a Bash subshell included. Nothing persists between calls here, but the paths after a `cd` would be judged from the folder before it. The call's own working directory is the way to run somewhere else: the guard is shown that folder.
- **A patch sent through the shell**: `apply_patch` as a word a shell would run - first in the call, inside a nested shell or an argument list, behind a launcher, with a `.bat` or `.ps1` suffix, in code a one-liner runs, or as patch text beside the tool's name. The guard cannot read it there. The refusal says to send it with the `apply_patch` tool itself. A search for the word passes.
- **An interactive session**: a shell or interpreter started with nothing to run or told to stay open (`pwsh`, `bash -i`, a bare `node` or `python`, `python -i x.py`, `pwsh -NoExit ...`, `cmd /k`, `deno repl`). What is typed into a running command fires no hook, so the session itself is refused. One that is given code, a script or a query flag (`node x.mjs`, `node --version`, `bash -lc "..."`) passes, and so does one that reads its script from a pipe.
- Every command is judged twice, as written and with its shell comments blanked, so a `# it's` comment cannot hide a later line.

**An `apply_patch` call** - the patch is read file by file: a written path is the target of `*** Add File`, of `*** Update File`, or of the `*** Move to` under one; a removed path is the target of `*** Delete File`, or an `*** Update File` that carries a `*** Move to`.

- A written path matching `PROTECTED_PATHS` (top of `guard.mjs`; case-insensitive on Windows and macOS): the generated and externally owned files, filled at install (`INSTALL.md`). A placeholder left unfilled reads as an empty list and protects nothing.
- A written or removed path under `.git`, or one of **the layer's own files**: `.codex/hooks/**`, `.codex/hooks.json`, `.codex/rules/**`, `.codex/agents/**` and `.codex/config.toml` (the project's Codex configuration can switch hooks off). The developer changes those, never a session.
- Any added line carrying an en dash (U+2013) or an em dash (U+2014), in a patch that writes at least one project file; every other dash-like character passes.
- More than one removed project path in one patch, and a removed path matching `PROTECTED_PATHS`.
- A `*** Move to` that brings a file into the project from outside it: its lines were never in a patch, so nothing read them. The refusal says to add it with `*** Add File`.
- A patch in which no file header can be found.
- A path outside the project is never checked: a scratch file in the temp directory may contain anything.

**Every call**

- **A misfilled `PROTECTED_PATHS`** (a bare string, a broken array, a bad regex) **refuses every call**, naming the list, until the developer fixes it: nothing else could tell anyone that the list protects nothing.
- A session whose working directory is outside the project this guard is installed in is refused whole: the guard of one tree would otherwise pass another tree's files as "outside the project".

**The write fence, by agent.** A Codex agent has no tool list of its own, so the guard is what keeps a read-only agent read-only. `CODEX_FENCED_AGENTS` in `guard.mjs` is read by the `agent_type` of the call: `drift` and the built-in `explorer` may write or remove no project path; `hunt` only a compile-probe path its own instructions never use in this layer. **A fenced agent may not start or task another agent** - the other one would not be fenced. The names `gate`, `twins` and `comments` are reserved for a larger layer and match nothing here. A project's own editor agent gets an entry there - the developer's edit.

**Path rules.** Codex scopes instructions by directory only, so the guard carries the layer's path-scoped rules. Every `*.md` in `.ai-layer/rules/` is a rule; its globs are the items of the `paths:` block list in its frontmatter, read the way Claude Code's rule loader reads them (a brace group expanded, a trailing `/**` stripped, a glob without a slash matching a name at any depth, a match on a folder covering everything under it), so one rule file reaches the same files under both tools. **Once every other check has passed, the first patch that writes a path a rule reaches is refused**, with the rule file's path and "read it in full, then retry this patch" - once per session and agent. What was shown is noted as empty files under `ai-layer-rules/` in the OS temp directory; on a `SessionStart` after a compaction or a clear the session's notes are deleted, and folders nobody touched for 14 days are pruned. With no usable session id, or when the note cannot be written, nothing is refused and the same sentence goes to the model as context. A glob may be followed by a YAML comment. A file moved out of a ruled folder brings that folder's rule too. `node .codex/hooks/guard.mjs --harness codex --rules-for <file>...` prints the rule files that reach those paths without patching anything - `--rules-for` and its files come last. Only files directly in `.ai-layer/rules/` with a lower-case `.md` are read.

**Why both a rules file and a hook.** `.codex/rules/git.rules` forbids the banned git verbs by the command's leading words only: `git -C <path> commit`, a quoted full path to the binary, a command with a redirect or a substitution, and a git call inside an interpreter one-liner all walk past it. The guard catches those forms. Both are backstops behind the rule in `AGENTS.md`. Never add an `allow` rule there: it runs its command outside the sandbox without asking.

**Refused though harmless - known.** `guard.mjs` fails closed: where it cannot tell a harmless command from a banned one, it refuses. The cases below are known, not defects to report, and each has a way round.

- **A shell comment in the command**: a quoted string after a `# it's` comment is read as a command, trailing comment words as arguments (`rm old.ts # orphaned` counts two paths, `cp a b # backup` copies onto `backup`), and a `;`, `|` or `&` in a comment before a `cd` word as a `cd`. Drop the comment and say it in the reply.
- **A `cd` word the guard cannot place**: a `cd` line inside a heredoc body a shell reads, behind an unquoted `cmd /c`, after a `;` in a backtick body, after a `case` pattern's `)` inside a subshell or after a line continuation; a PowerShell hashtable key named `cd`; `echo x | cd`. Use absolute paths or the call's working directory; rename the key.
- **Paths**: a move target whose own name holds a comma; one path spelled relative and absolute in one call, read as two deletes; a copy or a `find -maxdepth 1 -delete` into a folder above the project, and a glob, or a bracketed name that does not exist as written, directly under one; a bracketed name escaped instead of quoted (`rm app/\[slug\]/page.tsx`); a `\\?\UNC\` path. Spell a path once, in one form, and quote a bracketed name; a step in a folder above the project is the owner's to run.
- **A target held in a variable**: a variable a leading statement sets to a literal and that is not named as scratch, beside a sibling value holding shell syntax or a quoted `~`, a Bash-managed name, or a comment, heredoc or `eval` in the command (`U="...?a=1&b=2"; O=/tmp/o; curl "$U" -o "$O"`, `O=/tmp/o.txt; echo hi > "$O" # note`). Name the scratch variable `$S`, or write the path out.
- **Text that only looks like a banned form**: a `git grep` word that looks like `-O` (`git grep -eOrder`, `-e "-O"`), a `--output` search pattern or path (`git log -S "--output"`) and `--output=<scratch path>`; search text holding `bash -c '...'` or `sh -c`; `[[ "$a" > "b" ]]`; a heredoc whose body a shell reads, or an unquoted one whose `$(...)` or backticks name a banned form; a `node -e` / `python -c` / `perl -e` one-liner, or a script fed to an interpreter on stdin, whose code quotes a git write verb as text; a `node` / `python` call with `-e`, `-r` or `-c` among its script's arguments that quotes one; `gh` or in-place tool words left unquoted in another command's arguments (`echo use sed -i`), or quoted in `gh`'s own (`gh search issues "gh pr create"`). Search for other text, or quote the text; put the code in a scratch file and run it by path.
- **A script on stdin, and arithmetic**: a script an interpreter reads on stdin that writes to a computed path, scratch included (`os.path.join(os.environ['TEMP'], ...)`); a write API, a git write verb, or quoted `gh` or in-place tool words anywhere else in a command that also feeds an interpreter or a shell on stdin; an arithmetic command `(( n > 0 ))`, which Bash may also parse as nested subshells. Write the script to a scratch file and run it by path; test with `[ "$n" -gt 0 ]`.
- **A patch that only talks about patches**: an `Update File` hunk whose context line itself reads like a file header (a doc that quotes `*** Delete File: x`) is judged as naming that path, and a patch that mixes a temp file with a project file has every added line dash-checked. Split the patch.

**Passes though it writes - known gaps.** The guard reads the text of one call, so a bypass nobody would type by accident is recorded here rather than closed with more guard code; a realistic slip, or a retry after a refusal, that passes is a defect to fix in `guard.mjs`. The self-tests pin two of them as `(allow, known gap)`.

- **Whatever a process the command starts writes**: a script file run by path, a package or task-runner script (a `format` script, `make fmt`, `./gradlew spotlessApply`), a build tool, a formatter missing from `formatterWrites`, a shell-out inside a one-liner (`execSync('rm ...')`, `os.system`, `subprocess`).
- **Writes no check lists**: a download into the working folder (`curl -O`, `wget` without `-O`), `ln`, `touch`, an archive unpacked into the tree (`tar -x -C`, `unzip -d`), git that writes a file (`format-patch` without `--stdout`, `archive -o`, `bundle create`), a release tool missing from `RELEASE_TOOL`.
- **A verb or a path the call builds at run time**: `git $v`, `git $(echo commit)`, an alias defined in the call (`git -c alias.co=commit co`), a verb concatenated for `Invoke-Expression`; a scratch variable climbing out with `..` (`$TMP/../../app/a.ts`); a quoted `~` path, which Bash keeps literal and writes inside the project.
- **A `cd` the guard cannot see as one**: behind `eval`, `builtin`, a backslash or quotes (`\cd`, `"cd"`), PowerShell's `iex "cd ..."`.
- **The wrong grammar for the shell**: a hook is not shown which shell a call asked for, so on Windows every command is read as PowerShell and elsewhere as Bash - text in the other grammar is judged by the wrong one; a quoted full path to `pwsh.exe` behind the call operator (`& "<path>/pwsh.exe" -Command "..."`) is not read as a shell body.
- **An interactive program outside the guard's list**: `ssh`, a debugger, anything started through a terminal wrapper (a database client or console is `backend-guard.mjs`'s, below). And an in-place tool named with its suffix (`sed.exe -i`).
- **`AGENTS.md`, `.agents/skills/` and `.ai-layer/`** are not among the layer's own protected files: a patch may write them as far as the guard goes (the default sandbox keeps `.agents/` read-only).

**Formatters.** The in-place formatters it refuses are the direct binaries (the JavaScript ones, `black`, `isort`, `ruff`, `gofmt`, `goimports -w`, `go fmt`, `golangci-lint run --fix`, `dotnet format`, `dotnet csharpier`, `cargo fmt`, `rustfmt`, `ktlint -F`, `google-java-format -i`, `clang-format -i`, `rubocop -a`). A build tool's formatting task (`./gradlew spotlessApply`, `mvn spotless:apply`) is the project's own script and passes - `AGENTS.md` Code Style says who runs the formatter.

## backend-guard.mjs - what it refuses

Under Codex it allows a call or refuses it. **Where its Claude Code form would ask the user, it refuses**, since Codex has no question: the reason names what the user can do instead - run the command in their own terminal when they asked for exactly that, or narrow a search. Every refusal cites `AGENTS.md`, "Data, secrets and the outside world". It reads a `Bash` call's command (by PowerShell grammar on Windows, by Bash grammar elsewhere) and an `apply_patch` call's patch, file by file.

**Secret files.** An env file (`.env`, `.env.local`, `.env-production`, `prod.env`, `.envrc`), a private key or keystore, an ssh key, cloud, registry and git credentials, a `secrets` or `credentials` file, a service-account key, terraform state and `terraform.tfvars`, Maven's `settings.xml` / `settings-security.xml`, the home `~/.gradle/gradle.properties`, the home `.npmrc` / `.yarnrc.yml` / `NuGet.Config` (a project's own stays readable), kubeconfig files, gcloud credentials (also by `$env:APPDATA`, `%APPDATA%` or Git Bash's `$APPDATA`) and `client_secret*.json` - plus the project's own list (`SECRET_RAW`). What stays readable: a name that says it is an example (`.env.example`, `.env.local.example`, `.env.sample`, `.env.template`, `.env.dist`, `example.env`), a `.pem` or `.key` whose name says it is public (`ca.pem`, `jwt_public.pem`, `fullchain.pem`), a `.pub` key, `known_hosts`, and a `secrets.yaml` under a chart's `templates/`. An env file with no secret in it that the project tracks on purpose (`.env.test`) is still refused until its built-in pattern in `SECRET_PATHS` (not the project list `SECRET_RAW`) is narrowed.

- **A patch** that writes one (`*** Add File`, `*** Update File`, a `*** Move to` destination), deletes one (`*** Delete File`) or moves one away - inside the project or outside it.
- A shell command that prints or copies one: a reader (`cat`, `head`, `grep`, `sed`, `Get-Content`, `tar`, `cp`, ...) with the file or a glob that spells the name (`.env*`, `*.env`) after it, at any depth - inside `$(...)`, a `bash -c` body, a `find -exec` - and `git show` / `git diff` / `git log -p` of one. A searcher's pattern, an `--exclude` and a copy's destination are not reads: `git grep "\.env" app`, `rsync --exclude .env`, `cp .env.example .env` (which `guard.mjs` refuses for its own reason, as a shell write into the tree). `< file` on stdin counts. So does an interpreter one-liner or a .NET file call whose string names one: `node -e "...readFileSync('.env')"`, `python -c "open('.env')"`, `[IO.File]::ReadAllText('.env')`, and another .NET reader of one (`[IO.StreamReader]::new('.env')`, a cast `([IO.StreamReader]'.env')`, `New-Object -TypeName System.IO.StreamReader '.env'`, `(Get-Item .env).OpenText()`, `((gi .env)).OpenText()`, a quoted method name `[IO.File]::'ReadAllText'(...)` - and `.Delete()` / `.MoveTo()` as a delete), its provider form (`${C:\app\.env}`) and a quoted literal in parentheses or an array (`Get-Content ('.env')`, `gc(".env")`, `@('a', '.env')`). An archive, a recoding or a Windows copier copies one too (`zip`, `Compress-Archive`, `gzip`, `iconv`, `perl -pe`, `certutil -encode`, `openssl base64`, `robocopy`, `xcopy`; a copy whose target an option names, `cp -t /tmp .env`, `Copy-Item -Destination x -Path .env`), and so does an upload of one - a value spelled `@file` or `<file` (`curl -F "f=@.env;type=text/plain"`, `--data-binary @.env`), the value of `-T`, `--upload-file` or `-InFile`, a `-Form` entry, a mail's `Send-MailMessage -Attachments` (or the files piped into it, `Get-Item .env | Send-MailMessage ...`); a hash (`certutil -hashfile`), a key generation (`openssl genrsa -out`), `zip -x .env`, a client certificate (`curl --cert x.pem --key x.key`) and a URL path do not. **A copy or archive of a whole folder** is walked like a search, past its own exclusions: `tar -czf b.tgz .`, `zip -r b.zip .`, `Compress-Archive -Path config` (or `-Path app,.`), `Copy-Item -Recurse config x`, `cp -r . /tmp/bk`, `robocopy . x /E` are refused with a secret file in the folder; `tar --exclude=.env`, zip's `-x` and robocopy's `/XF` keep one out. A path is also judged as it resolves from the call's folder, so a project entry such as `config/local\.settings\.json$` holds for `cat local.settings.json` run inside `config`; and by the name Windows opens - a trailing dot or blank and a stream suffix (`.env.`, `'.env '`, `.env::$DATA`) are the file itself.
- **A wildcard that takes one on disk**: the folder a reader's wildcard names is listed, and a secret file among the names it matches is refused - `cat .e*`, `cat .[e]nv`, `gc .en*`, `Get-Content *`, also after `-Path` (`Get-Content -Path config\*`) and inside a PowerShell comma list (`gc app\main.py,.e*`). Under Bash a wildcard that opens the name skips dot files (`cat *` passes in a folder whose only secret is `.env`), as the shell does; PowerShell's does not. A wildcard after an option that takes a filter or a pattern (`rg -g '*.json'`, `find -name`, `--include`) is never expanded.
- **Names piped into a reader**: a PowerShell listing or item piped into a cmdlet that reads each file (`Get-Item .env | Get-Content`, `gci -Filter .env* | gc`, `gci | gc` - no operand is the folder itself; `gi .env | % { gc $_ }` too), and under xargs the names `echo` prints or the files `ls` lists (`echo .env | xargs cat`; `ls` without `-a` hands on no dot file). Under Bash `ls | cat` only prints the names and passes; so does a listing piped into anything that does not read files (`gci | Sort-Object Name`).
- **A delete or move of one** from the shell - by name, in a PowerShell comma list (`Remove-Item a.txt,.envrc`), by a wildcard that takes one, behind a deleting `find` (`find . -name .env -delete`), or piped into a remover (`echo .env | xargs rm`, `Get-Item .env | Remove-Item`): a secret file holds values only the owner has. A move's destination is not removed (`mv .env.example .env` passes as far as this hook goes), a filter's value is not either, and a PowerShell remover's `-Exclude` / `-Include` / `-Filter` decide what its wildcard takes (`Remove-Item app\* -Exclude .env.local` passes beside `app\.env.local`), and `git rm --cached .env` only stops tracking it. A deleting walk over a tree too large to check is refused, as a search is.
- **A search that reads a whole folder with one in it, at any depth**. The hook walks the folders the command names (none: the current one) and refuses when a secret file is among the files the command would read:
  - a recursive `grep` (`grep -rn KEY .`, `grep -rn KEY apps` over `apps/api/.env`);
  - `rg` told to read ignored or hidden files (`-u`, `-uu`, `--no-ignore`, `--hidden`) - judged as a search of every file;
  - `findstr /s`, and a wildcard handed to `findstr` or `Select-String` (`Select-String -Path * -Pattern KEY`), which reads the matching files of that one folder;
  - a file listing piped into `Select-String` (`Get-ChildItem -Recurse | Select-String KEY`, `gci -r | sls KEY`; without `-Recurse`, the folder's own files);
  - a `find` that hands its files to a reader (`find . -type f | xargs grep KEY`, `find . -type f -exec grep KEY {} +`).

  The walk skips `node_modules` and `.git`, which a search almost never means; build output (`build`, `dist`, `target`, ...) it walks, as grep does, unless the command's own `--exclude-dir` names it. What passes: `git grep` over files git ignores (next bullet for the ones it does not), and plain `rg` where it is installed; a search in a folder that holds no secret; and a filter that keeps every secret out - `--exclude` / `--exclude-dir` / `--include`, `rg -g` or `-t`, `-Include` / `-Filter` / `-Exclude`, find's `-name` and `-maxdepth`, a wildcard no secret's name matches (`*.py`), a listing of names only (`-Name`). **Past 20 000 entries the tree is too large to check, and the search is refused**: name the folders, exclude what it must not read, or use `git grep`.
- **A `git grep` that prints the lines of a secret file git does not ignore** - one it tracks (a config file on the project list, say), or with `--untracked` one it merely does not ignore - without `-l` / `-L` / `-c` / `-q`. What passes: a list of file names (`git grep -l`), and a pathspec that leaves the file out (`-- '*.java'`, `':!config/app-prod.yml'`). A keystore (`.jks`, `.p12`, `.pfx`) is binary and is not printed, so it does not count here - unless `git grep -a` reads it as text. The secret lists are tested against the whole path wherever the search starts. A revision handed to `git grep` (`git grep KEY HEAD`) is not looked into.
- `docker compose config` (and its alias `convert`), which prints the file with every env value filled in - unless `--services` / `--volumes` / `--profiles` / `--images` / `--networks` / `--hash` / `-q` makes it print names only, or every `--env-file` is an example file.
- Loading one into a process prints nothing and passes: `. ./.env`, `docker compose --env-file .env`.

**Frozen files.** A path matching the frozen list (`FROZEN_RAW`: the migration files; case-insensitive on Windows and macOS) that is on the upstream default branch as of the last `git fetch` - the hook never fetches (`origin/HEAD`, else `origin/main`, else `origin/master`); with no such ref - no remote, or a repo made with `git init` whose default branch has another name, where `git remote set-head origin --auto` creates it - one git tracks:

- A patch that writes, deletes or moves it (`*** Update File`, `*** Delete File`, an `*** Update File` with a `*** Move to`), and a shell delete or move of it, of its folder or of a glob that reaches it. A migration the task itself created is not tracked yet and stays editable, and a new file in the folder is always allowed.
- A shell delete or move is judged where the command itself removes: a remover at its head (`rm`, `mv`, `Remove-Item`, `del`, ..., behind `sudo` or `xargs` too), `git rm` / `git mv`, `find -delete` and `find -exec rm` over the folders they start from, and `cmd /c del`. A remover word that is another tool's verb, with a name after it, is not one: `docker rm -f db`, `docker compose rm -sf db`, `npm rm db` (`docker volume rm` is refused as data, below).
- A migration committed only on the working branch stays editable: it is still the developer's to fix before the merge.

**Commands that leave the machine.** One built-in list (`FORBIDDEN`), plus the project's own (`FORBIDDEN_RAW`):

- **deploy and infrastructure**: `kubectl` and `helm` verbs that change a cluster (the refusal names the local retry: `--context kind-<name>` for `kubectl`, `--kube-context` for `helm`), `terraform` / `pulumi` apply and destroy, `ansible-playbook` without `--check`, the write verbs of the cloud CLIs `aws`, `gcloud`, `az`, `gsutil` and `azcopy` (what creates, changes, deletes, runs, scales, swaps or publishes, an upload to a bucket and a copy from one bucket to another included; a download, a `list` / `describe` / `show` / `get-*` and `aws configure` / `gcloud config` / `az account` pass), `az acr build|run`, `skaffold run|dev|deploy|delete` without a local `--kube-context`, `dotnet publish|build|msbuild` and `msbuild` with a `PublishProfile=`, `WebPublishMethod=` or `DeployOnBuild=true` unless a folder profile, the deploys of the common deploy and hosting tools, and a docker call that changes another host (`-H`, `--context`, `DOCKER_HOST` or `DOCKER_CONTEXT` naming one, on the call or assigned earlier in the same command with `export` / `$env:`; `ps`, `logs` and the other reads pass).
- **publish**: an image push (`docker`/`podman` push or a `--push` build, Gradle `jib`, Maven `jib:build`, `bootBuildImage --publishImage`, `spring-boot:build-image` with publish on, `ko build|apply|resolve` without `--local`, `crane push|copy|delete|tag|mutate|append|rebase`, `buildah push` and `buildah manifest push`, `skopeo copy|sync|delete` to a registry that is not local, `oras push|attach|cp`), a package publish (npm, PyPI, crates, gems, Maven, Gradle, sbt, NuGet, Hex), a release.
- **What passes**: a command carrying `--dry-run`, and a command aimed at this machine by its own words - `--endpoint-url` on localhost (an emulator), the `gcloud` emulators, `--context` naming a local cluster (`kind-*`, `k3d-*`, `minikube`, `docker-desktop`) and `kubectl config use-context` switching to one, an `azcopy` target on localhost, an image push to a registry on localhost, a `--push` build whose every tag is on localhost, a jib build whose `-Dimage=` / `-Djib.to.image=` is on localhost, a folder publish profile, `jibDockerBuild` / `jib:dockerBuild`. A `kubectl apply` that names no context is not known to be local and is refused. The default sandbox has no network anyway; what passes here may still be stopped there, and is then the developer's to run.
- The lists are closed: a deploy tool or a cloud verb they do not name, and a task-runner target that wraps one, go into the project's forbidden list.

**What the Claude Code form asks about - refused here, the user runs it in their own terminal.**

- **Commands that destroy data**: `docker compose down -v`, a volume or system prune, `DROP` / `TRUNCATE` / a `DELETE` or `UPDATE` with no `WHERE` handed to a database client (`-c`, `Invoke-Sqlcmd -Query`, a pipe from `echo` or, in PowerShell, from a quoted string, a heredoc), a cache flush, and the migration tools' wipe commands (`migrate reset`, `migrate:fresh`, `db:reset`, `flush`, `downgrade base`, `database drop`, `database update 0`, `down -all`, `clean`), a rollback past one step or to a target the hook cannot size (`alembic downgrade -2` or to a revision, `db:rollback STEP=3`, `db:migrate VERSION=...`, `manage.py migrate <app> <migration>`, `dotnet ef database update <migration>`, golang-migrate's bare `down`, `goose down-to`, `ecto.rollback --step 3`, a liquibase rollback past one changeset - the CLI's or the Maven / Gradle plugin's - `db:migrate:undo --to`, golang-migrate's `goto`), and a delete or move of a database's data folder, outside the project too (`/var/lib/postgresql/...`, a `pgdata` bind mount, `/data/db`, `"$PGDATA"`). A step back by one migration passes - the edit-and-retry loop on the task's own migration - and a redirection is never read as a target (`dotnet ef database update 2>&1 | tail`, `migrate orders > migrate.log`). `migrate` as a package script run through `npm`, or a compose profile, is not golang-migrate.
- **Rewriting the migration history**: `alembic stamp` / `flask db stamp`, `manage.py migrate --fake`, `flyway repair` (and `flywayRepair`), golang-migrate's `force`, `liquibase changelog-sync` and `clear-checksums` (the plugins' `changelogSync` and `clearCheckSums` too), `dotnet ef migrations remove`, `prisma migrate resolve`.
- **A printed secret from a cluster or a store**: `kubectl get secret` with an output that prints the values (`-o yaml|json|jsonpath|go-template|custom-columns`; a plain list of names and `describe`, which shows byte counts, pass), a read from a cloud secret store that prints the value (`aws secretsmanager get-secret-value`, `aws ssm get-parameter` / `get-parameters` with `--with-decryption`, `gcloud secrets versions access`, `az keyvault secret show`, `heroku config` and `config:get`; a list of names, a `describe` and a parameter read with no decryption pass), a secret a tool keeps or decrypts (`dotnet user-secrets list`, `rails credentials:show`, `sops -d`, `vault kv get` / `vault read`, `op read` / `op item get`).
- **Another host**: `ssh` / `scp` / `sftp` / `rsync` and PuTTY's `plink` / `pscp` / `psftp` to a host that is not this machine (`ssh -T git@<host>`, a key check, passes), `winrs -r:<host>` and `psexec \\<host>`, PowerShell remoting to another computer (`Invoke-Command` / `Enter-PSSession` / `New-PSSession` with `-ComputerName`, `-HostName`, `-ConnectionUri` or the computer as a plain word - before or after the script block, inside a `ForEach-Object` or `Measure-Command` block too -, a session handed over with `-Session`, `-SSHConnection`, `-ToSession` or `-FromSession`, and any cmdlet's `-ComputerName` / `-Server` / `-CimSession`, `Restart-Computer prod01` - but not a probe's, `Test-Connection`; a host the hook cannot tell is this machine, `$h`, counts too), a tunnel to a database elsewhere (`kubectl port-forward` without a local `--context`, `cloud-sql-proxy` - behind `nohup` or `sudo`, by its release asset's name or as a `docker run` image too - `gcloud sql connect`, `gcloud compute start-iap-tunnel`, `az postgres|mysql ... connect|execute`, `heroku pg:psql`, `fly proxy`, `railway connect`), a database client or dump tool whose own words name another host (`psql`, `mysql`, `pg_dump`, `mysqldump`, `mongodump`, `mongoexport`, `redis-cli`, ... with `-h` / `--host`, sqlcmd's `-S`, a database connection URL, a libpq connection string, a `PGHOST=` or URL assignment before it or earlier in the same call; one run inside a container passes - `docker exec`, compose, `kubectl exec` on a local cluster, a `docker run` on a network it names - while a `docker run` of a client image on no network is refused). A host the hook cannot tell is this machine is refused as well: a service name typed outside a container runner (`psql -h db`), a variable (`-h $DB_HOST`).
- **A search over a tree too large to check** (above): narrow it instead.

Neither `--dry-run` nor a local endpoint lifts these.

**Only under Codex.**

- **An interactive database session or console**: a database client left open with no statement (`psql`, `mysql`, `sqlite3`, `mongosh`, `redis-cli`, `sqlcmd` and the others in `SESSION_CLIENTS`, with no `-c`, `-e`, query file or piped input), a framework console (`rails c`, `manage.py shell` / `dbshell`, `artisan tinker`, `flask shell`), a shell or client left open in a container (`docker exec -it db psql`, `docker compose exec app bash`, `docker run -it <image>` with nothing after the image), a container attach (`docker attach`, `docker start -ai`) and an interpreter prompt in a container (`python`, `python -i x.py`, `python -m IPython`, `deno repl`; `python --version` passes). What is typed into a running command fires no hook, so the session itself is refused: pass the statement with the client's own flag or a file, or the developer opens the session in their own terminal.
- **A misfilled project list** (broken JSON, not an array of strings, a regex that does not compile) **refuses every call**, naming the list, until the developer fixes it: no message of the Claude Code form reaches anyone here.
- **A command it cannot read through**: a shell nested more than three deep, an encoded command it cannot decode (pwsh's own `-EncodedCommand` only, not a `-e` of another tool or of the script), and a call that stops the hook after it was parsed, are refused rather than passed unread.

**What is not judged.** A segment whose head only searches or prints (`grep`, `echo`, `git`, `cat`, ...), so `git grep -n "terraform apply" README.md` is a search; a quoted argument with spaces in it, which is a message, a filter or a name (`-m "drop unused column"`, `-k "publish and not slow"`) unless a shell runs it; a heredoc body, or a PowerShell here-string, unless a shell (`bash`, `iex`, `Invoke-Expression`, `pwsh`) or a database client reads it - an apostrophe inside a here-string hides nothing after it, and a `<<` inside quotes opens no heredoc. A block or a keyword around a command is not a command of its own: `{ rm .env; }`, `& { ... }`, `1 | % { ... }`, `if ...; then ...` are judged by the command inside, and so are `foreach { ... }`, `%{ ... }`, `.{ ... }`, `ForEach-Object -Begin { ... } -Process { ... }` (each block), `(gci).ForEach({ ... })`, `| & { process { ... } }`, `Invoke-Command` / `Measure-Command` / `Start-Job` blocks. A PowerShell block comment (`<# ... #>`) is blank space, so a command after it is judged - also right after a closing quote or another comment; inside a word or a string it is no comment. Braces need no blank around them: `&{process{gc $_}}` is a block like `& { process { gc $_ } }`. A parameter joined to its value (`-Path:.env`, `-Path: .env`, `-Recurse:$true`) is read as the parameter and the value, a parenthesised argument (`-TotalCount (10)`, `-Force:(1)`) as one more argument - its own content is judged as a command - and a PowerShell comma list as several arguments. A glob is matched without a regex, so a long or unbalanced one (`--include=[`) can neither time the hook out nor stop it.

**What it cannot see** - it reads the text of the call, so it misses a script file that runs the same command, SQL in a file handed to a client (`-f wipe.sql`, `Invoke-Sqlcmd -InputFile`), the Az, AWS and SecretManagement PowerShell modules (`Remove-AzResourceGroup`, `Publish-AzWebApp`, `Write-S3Object`, `Get-AzKeyVaultSecret -AsPlainText`, `Get-SECSecretValue`, `Get-Secret -AsPlainText` - name the ones the project uses in its forbidden list), a wildcard in a folder part (`Get-Content conf*\local.settings.json`), a PuTTY saved session (`plink -load prod`, whose host is in the registry), a .NET delete of a migration (`[IO.File]::Delete(...)`, `[IO.Directory]::Delete(...)`), a FileInfo or .NET read handed its file over a pipe or a variable (`gi .env | % OpenText`, `gi .env | % { [IO.File]::ReadAllText($_) }`, `(Get-ChildItem -Force)[0].OpenText()`) or a type named through `using namespace System.IO`, a `kubectl attach` under the other tool's form, a secret printed from the process environment (`printenv`), a secret reached through a variable, a loop or a subexpression (`$p = '.env'; gc $p`, `Get-Content (Join-Path . '.env')`, `Get-Content (Resolve-Path .env)`), a chain of more than one pipe (`ls -a | grep env | xargs cat`), a here-string assigned to a variable and used later, a delete inside a launcher's argument list (`Start-Process pwsh -ArgumentList '-c Remove-Item .env'`), a tool named with `.com`, a search fed from a list the hook does not read (`git ls-files -o | xargs grep`, a `find` with a `-path` or `-regex` test, a listing filtered through `Where-Object`), a tool that parses a key (`openssl rsa -in ... -text`), and a request sent to a shared host. A home-folder path is expanded only when it starts with `~`, `$HOME`, `${HOME}`, `$env:USERPROFILE`, `$env:HOME` or `%USERPROFILE%`. It reads a database host only from the command's own words: one a client takes from its environment, an env file or a config file it cannot see. Those are `AGENTS.md` "Data, secrets and the outside world".

**Refused though harmless - known.** `docker run -it <image>` with no command is refused even when the image runs a server: name the command after the image, or drop `-it`. A copy or archive of a folder that holds an env file of its own (`Compress-Archive -Path app` beside `app\.env.local`) is refused, as it would carry the file. A cmdlet's `-Server` naming another machine counts as another host even where it only reads (`Get-ADUser -Server dc01`).

## The project lists

`PROTECTED_PATHS` in `guard.mjs`, and `FROZEN_RAW`, `SECRET_RAW` and `FORBIDDEN_RAW` in `backend-guard.mjs`: each a JSON array of regex sources inside a raw string, filled at install, with a regex backslash doubled once as in a `.json` file. An unfilled or empty one reads as an empty list. **The path lists are tested against the absolute path with forward slashes, so an entry matches the path's tail and never starts with `^`** (`"db/migrations/[^/]+\\.sql$"`); a frozen entry names the numbered files only, never a file a new migration has to edit - a master changelog, an include list, a repeatable script - and matches whatever the case on Windows and macOS, as the secret list does everywhere. The forbidden list is tested against one command segment with its words joined by single spaces (`"\\bmake\\s+deploy(?!\\S)"`; a `\\b` after the target would refuse `make deploy-docs` too) and always refuses - a dry run does not pass it. **A misfilled list refuses every call**, in both hooks, naming the list, until it is fixed. Run the self-tests after every edit.

## Self-test

```text
node .codex/hooks/tests/guard-test.mjs
node .codex/hooks/tests/guard-shell-test.mjs
node .codex/hooks/tests/backend-guard-test.mjs
node .codex/hooks/tests/upkeep-nudge-test.mjs
```

Every case line must read `ok`, and each suite ends with `N passed, 0 failed`. Each guard suite runs the shared file in both forms: first the cases of the other tool's form (exit codes), then a block that starts the guard with `--harness codex` and feeds it payloads in the shape Codex sends - that block is the one this layer runs on, and the first keeps an edit to a shared check honest. **The shell suite needs the source-directory placeholder filled first** (the install does it): it builds its paths from that value, and an unfilled `<...>` reads as a redirect, so an unfilled copy fails the cases built from it, with nothing wrong with them. `guard-test.mjs` is meaningful from the first minute: its only placeholder paths are the fence cases, and the unfilled guard carries the same placeholder, so they still match. Once the source directory is filled in `guard.mjs`, it is filled in those cases too, or the probe case fails. Add one case per entry in `PROTECTED_PATHS`, in the `--harness codex` block of `guard-test.mjs`: `['patch: generated client (deny)', 'deny', P(patch('*** Update File: <a path the entry matches>', '@@', '+x'))],` (the two commented lines in its first block show the other form's shape); the matching itself, case folding and a misfilled list are tested on temp copies of the guard with a known list.

`backend-guard-test.mjs` runs in four parts: the built-in checks against the installed hook in the other tool's form (exit codes, and `'ask'` where that form asks), in a folder the suite builds in the temp directory (an env file at its top, another in `app/`) so the project's own files never decide a walk or a wildcard; the three project lists against a copy of the hook with sample values in a throwaway git repo in the temp directory (the frozen cases make commits and remote refs of their own there, never in this tree), the same copy with the lists unfilled and misfilled, and part 4, the same copy started with `--harness codex` - the form this layer runs on: every former question a refusal, a misfilled list refusing every call, the interactive clients and consoles refused, and no reason naming the other tool's mechanisms. It needs `git` on the path. A few cases are timed: a long command must be judged well inside the hook's timeout. Add one case per entry of the three project lists at the marked place at the end of its first part (two commented lines show the shape; the matching is the same code in both forms).

Run them after every change to a hook or to a list. A regex that does not compile takes the whole hook down, and a hook that crashes lets every call through. `.codex/rules/git.rules` is checked with `codex execpolicy check --pretty --rules .codex/rules/git.rules -- git commit -m x` (it must answer `forbidden`), which also proves the file still parses: its `match` and `not_match` lines are examples the engine verifies on load.

## Switching a rule off

**Every edit below is the developer's own**: the guard refuses a session's write to `.codex/hooks/`, `hooks.json`, `rules/` and `agents/`, and a changed hook must be reviewed again before it runs (Trust, above). A rule lives in up to four places - the `AGENTS.md` text, a `guard.mjs` check, a `.codex/rules/` file and the test cases. Remove all of them together, or the rule half-holds and the agent argues with it.

- **The never-commit policy** (the one the install asks about):
  - `AGENTS.md`: the "Version Control - Never Commit or Push" section, all but its `Layer tracking` line.
  - `.codex/rules/git.rules`: the whole file.
  - `guard.mjs`: the `deny(...)` calls behind the `gitWrites`, `releaseWrites` and `ghWrites` checks in the per-segment loop, and behind `gitWritesAnywhere` for a script read on stdin; the lists they read (`GIT_WRITE_VERBS`, `GIT_WRITE_SUBCOMMANDS`, `RELEASE_TOOL`, `GH_MUTATING`) can go once nothing else reads them. Keep the `gitReadEscapes` check: it stops `git grep -O<cmd>` from running a program, which has nothing to do with committing.
  - `tests/guard-shell-test.mjs`: the git, release-tool and `gh` cases marked `(deny)`, in both blocks, which now fail, and the `git commit` case in `tests/guard-test.mjs`.
  - **With the ban gone the frozen check loses part of its footing** - with no remote it trusts that only the owner commits - so narrow it or drop it too.
- **One backend check**: empty its project list and delete its entries from `SECRET_PATHS` or `FORBIDDEN` (a `RegExp` line each in `SECRET_PATHS`, a `rule(...)` line each in `FORBIDDEN`) in `backend-guard.mjs`, the matching bullet of `AGENTS.md` "Data, secrets and the outside world", and the cases in `tests/backend-guard-test.mjs` that expect its refusal, in part 4 too. To let a file the list calls secret be read (a tracked `.env.test`, a fixture key), narrow that one pattern. To let the data commands through, delete the `data` rules. A project that deploys from the agent's session on purpose deletes the `deploy` rules it uses, not the kind.
- **The `cd` rule:**
  - `AGENTS.md`: the "Never `cd` or `Set-Location` in a command" bullet.
  - `guard.mjs`: the `if (CHDIR.test(head))` block and the `CHDIR` constant. No rules file belongs to it.
  - `tests/guard-shell-test.mjs`: the `cd`, `Set-Location` and `pushd` cases marked `(deny)`, in both blocks.
- **The dash rule has no off-switch.** The layer's own files and the guard's messages rely on plain hyphens, so it stays on in every install.
- **A whole hook**: remove its `PreToolUse` entry from `.codex/hooks.json`. Without `guard.mjs` what remains is `git.rules`, which matches a command's leading words only (see "Why both a rules file and a hook"); nothing at all is left against shell writes into the tree or an interactive shell, no agent is fenced, and no path rule is handed over any more. Without `backend-guard.mjs` nothing checks a secret, a frozen migration, a deploy or a database session but the text of `AGENTS.md`.

A new rule goes in with a test case in the same change. Both guards are regex over shell text: a rule with no test is a rule that works until the first quoted path.

## upkeep-nudge.mjs - the upkeep reminder

Registered as `SessionStart` (startup, clear). Reads the date in `.ai-layer/.last-maintain` (committed with the layer in team mode, per machine in personal mode; one `YYYY-MM-DD` line, written by `maintain-ai-layer`, its `init` run included) and, when it is 30 days old or more, more than a day ahead, missing or unreadable, hands the model a line telling it to tell the user once that `$maintain-ai-layer` (its default `deep` mode) is due - never to start it. It finds the project by its own location, like the guard. Silent in a linked worktree (the nearest `.git` is a file), since the pass runs in the main tree. It reports and never blocks, and costs tokens only on the day it speaks. Self-test: `node .codex/hooks/tests/upkeep-nudge-test.mjs`, every line `ok`.
